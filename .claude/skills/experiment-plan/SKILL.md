# Experiment Plan

输入一句话选题，输出一个能照着跑的实验目录。

## 边界

这个 skill 设计**过程**，不预设**结果**。

- 步骤、交付物、要记什么数据 → 这里定
- 结论、判断、实验跑出来是什么 → 跑完才有，不许预填

不要往 `Log` / `Data` / `What Worked` / `What Failed` / `Conclusion` 里写任何内容。这五段只留标题。预填等于污染实验——人会不自觉地往预设的答案上靠。

同样不要编造用户没说的工具、版本、环境。缺什么就问。

## 流程

### 第一步：审选题

一句话选题通常不够开工。先确认这四件事，缺了就问，不要猜：

1. **对象**——测什么工具 / 什么方法 / 哪几个之间对比
2. **任务**——用什么具体任务去测。必须是真实任务，不是 toy example
3. **判据**——怎么算做完了、怎么算某一方赢了
4. **反直觉点**——你预期会推翻什么常见说法

第 4 项是选题价值的核心，和 `content-forge` 判断内容价值用的是同一个标准。如果用户答不上来，直说：这个选题可能只能产出一篇平庸的工具介绍，建议换角度或换对比对象。不要硬着头皮往下做。

**拒绝教程式选题。** 「XX 怎么用」「XX 使用教程」不是实验。遇到这类输入，改写成结构性问题再确认：

| 输入 | 改写 |
| --- | --- |
| Claude Code 怎么用 | 同一个真实需求，Claude Code 和 Cursor 谁的返工次数更少？ |
| MCP 介绍 | MCP 能不能替掉我现在手写的三个脚本？代价是什么？ |

### 第二步：定规模

第一个实验不要设计成 30 天。

单次实验的合理规模：**半天到三天能跑完，产出 3-5 条量化数据**。大主题拆成多个实验，用 monorepo 交叉引用——这正是 lab 用单仓的理由。

如果用户的选题明显超过三天，提出拆分方案再继续。

### 第三步：建目录

目录建在 **`silicon-leap-lab` 仓库**的 `experiments/` 下。这个 skill 装在 forge，也可能从任意目录调用——先确认当前工作目录是不是 lab，不是就定位到 lab 仓库，找不到就问用户要路径。**绝不在 forge 或其他仓库里建 `experiments/`。**

目录名：`experiments/YYYY-MM-<slug>/`，用当前年月，slug 用 kebab-case 英文。

写两个文件：

**`README.md`**——七个标题齐全，只填 `Question` 和 `Setup`：

```markdown
# <实验标题>

## Question
<一句话。第一步确认的那个问题。>

## Setup
<工具、版本、环境、任务清单。写到别人能复现的程度。>

## Log

## Data

## What Worked

## What Failed

## Conclusion
```

标题文本一字不能改，`content-forge` 按标题解析结构。

**`plan.md`**——剧本，结构如下：

```markdown
# 实验剧本：<标题>

## 判据
<怎么算这次实验有结论。写死，跑的过程中不许改。>

## 预期反直觉点
<你预期会推翻什么。跑完回来对照，猜错了本身就是内容。>

## 步骤

| # | 做什么 | 交付物 | 记什么数据 | 录哪段 |
| --- | --- | --- | --- | --- |
| 1 | | | | |

## 数据字段
<这次实验要记录的字段定义，至少覆盖：耗时、token 或调用次数、成功/失败/人工干预次数、1-5 主观评分。每个字段写清单位和记录时机。>

## 录制清单
<按 `NN-描述.cast` 命名列出计划录的片段。哪些必录，哪些可选。>

## 已知风险
<可能卡住的地方、可能拿不到数据的地方。提前想到就不会中途放弃。>
```

「记什么数据」这一列不许留空。步骤跑完当场记，事后补是补不出来的。

### 第四步：报告

告诉用户：

- 建了哪些文件
- 预计耗时和步骤数
- 哪些前提还没确认（工具版本、账号、环境）
- 第一步具体从什么动作开始

## 硬约束

- 五个结论类段落只留标题，不预填。
- 不编造用户没确认的工具、版本、环境。
- 教程式选题先改写，改写不掉就说清楚为什么这个选题不值得做。
- 每个步骤必须有交付物。说不出交付物的步骤是想象，不是计划。
- 单次实验控制在三天内。超了就拆。
- 剧本是拿来跑的，不是拿来看的。步骤写到「照着做不用再想」的粒度。
