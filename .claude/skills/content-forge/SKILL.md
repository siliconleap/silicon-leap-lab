# Content Forge

把一次实验的原始素材，先整理成中立事实摘要，再按平台配置生成对应内容包。

## 边界

这个流水线负责事实蒸馏、平台适配、格式转换，不负责产出观点或替用户发布。

- 结论、判断、语气 → 留给人写
- 事实提取、结构、格式、跨平台改写 → 流水线做
- 平台账号操作、发布、排期 → 交给专门平台 skill 或人工

遇到实验 README 的 `## Conclusion` 为空时，**不要替用户编造结论**。生成其余部分，并在输出中明确标注结论待补。

## 流程

### 第一步：读取

读实验目录下的：

- `README.md`（必需）——按标题提取 Question / Setup / Log / Data / What Worked / What Failed / Conclusion
- `plan.md`（若存在）——开跑前的剧本。重点看「预期反直觉点」，和 README 实际结果对照：**猜错的地方就是选题最好的开篇**
- `notes/`——所有文件，作为过程细节的补充
- `data/`——量化结果
- `recordings/`——只列文件名和时长，用于视频脚本的片段标注

约定见 `docs/experiment-layout.md`。

若 `README.md` 缺失或标题不完整，先告诉用户缺什么，不要猜。

### 第二步：蒸馏中立事实

在生成任何平台内容之前，先产出一份结构化摘要（内部使用，不写文件）。这一步不考虑平台风格：

```
一句话结论:
核心问题:
测了什么:
关键数据: (3-5 条，必须来自 data/ 或 README 的 Data 段，不得杜撰数字)
有效的:
失败的:  (标注每一条的原因)
预期落差: (plan.md 的预期反直觉点 vs 实际结果。无 plan.md 则跳过)
最反直觉的发现:
可用录屏片段: (文件名 → 对应内容)
```

「最反直觉的发现」是选题价值的核心。如果找不到，说明这次实验的内容价值有限，直接告诉用户。

### 第三步：选择平台

读取 `platforms/` 下的平台配置。每个平台配置定义：

- 平台别名和触发词
- 输出文件和对应模板
- 写作风格、侧重点、排版要求
- 平台验收清单
- 是否需要下游发布 skill

默认生成所有已配置平台。若用户指定平台，只生成匹配平台。若用户指定的平台没有配置，先告诉用户缺哪个 `platforms/<id>.md`，不要临时硬编一套规则。

新增平台时，只加：

1. `platforms/<id>.md`
2. `templates/<id>/...`

除非平台选择逻辑变化，不要改本 skill 主流程。

### 第四步：平台渲染

用蒸馏结果填充被选平台声明的模板，写入实验目录的 `drafts/<platform>/`：

| 平台 | 配置 | 典型输出 |
| --- | --- | --- |
| 网站 / 静态站 | `platforms/site.md` | `drafts/site/blog.md` |
| GitHub | `platforms/github.md` | `drafts/github/readme-section.md` |
| 小红书 | `platforms/xiaohongshu.md` | `drafts/xiaohongshu/note.md`, `carousel-brief.md` |
| YouTube | `platforms/youtube.md` | `drafts/youtube/script.md`, `packaging.md` |

平台适配不是简单改长度。必须按配置改变开头、结构、证据密度、排版、素材需求和 CTA。

### 第五步：报告

生成后简要说明：

- 写了哪些文件
- 哪些部分是占位、需要用户补（尤其是结论）
- 数据是否充分，不足则指出缺什么
- 各平台还缺什么素材或人工动作
- 哪些平台适合交给下游发布 skill

## 各渠道的取舍

各平台来自同一份事实摘要，但取的部分不同。不要把 Blog 缩短当成社交文案，也不要把 Blog 念一遍当成视频脚本。具体规则以 `platforms/` 配置为准。

- **网站 / 静态站**——可信、可引用、可检索。保留方法、数据、复现信息、原始记录链接。
- **GitHub README**——最短。做了什么、结论是什么、怎么复现。
- **小红书**——封面和前三行决定点击。结论前置，短句，可扫读，配图脚本必须具体。
- **YouTube / 视频**——包装和留存优先。保留过程、现场、失败和卡住的瞬间；必须给标题、thumbnail、hook、章节、description、字幕和可切 Shorts。

## 硬约束

- 数字只能来自 `data/` 或 README 的 Data 段。没有数据就写「待补」，绝不估算。
- 不要写成教程口吻（「首先我们打开…」）。这是实验记录，不是使用说明。
- 标题不用「XX 使用教程」这类形式。用结构性问题或反直觉结论。
- 保留失败。失败是这类内容的主要价值来源，不要为了好看删掉。
- 平台配置的验收清单必须逐项检查；不满足就报告缺口，不要假装完成。
- 小红书、YouTube 等平台发布动作不在本 skill 内执行；只生成可交给发布 skill 的内容包。
