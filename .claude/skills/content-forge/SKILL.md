# Content Forge

把一次实验的原始素材，先整理成中立事实摘要，再生成一份由作者确认的短内容简报，最后才按平台配置展开内容包。

## 边界

这个流水线负责事实蒸馏、平台适配、格式转换，不负责产出观点或替用户发布。

- 结论、判断、语气 → 留给人写
- 事实提取、结构、格式、跨平台改写 → 流水线做
- 平台账号操作、发布、排期 → 交给专门平台 skill 或人工

遇到实验 README 的 `## Conclusion` 为空时，**不要替用户编造结论**。生成其余部分，并在输出中明确标注结论待补。

写作润色可以交给独立的写作 sub-agent，但它只能改善表达和结构，不能补造事实、作者判断或发布经历。事实、立场、平台账号与发布动作仍由人确认。

## 内容目标：真实记录也必须值得读

实验数据和过程记录要如实保留，但最终文章不能只是实验日志的缩写。每篇内容都应从一个**读者能认出的真实困境**切入：它可以是「输入很多却迟迟没有开始」「工具齐全却交付不了」「以为自动化会消除判断成本」这类普遍感受，再用作者这次真实经历和实验事实把它讲具体。

这条叙事线是文章的“影子”：不必反复喊口号，却要出现在标题、开头、关键转折或收尾中的至少两处，让读者知道这件实验与自己有什么关系。平台适配的目的不是把同一份数据改成不同长度，而是让不同读者愿意进入同一个真实问题。

边界同样严格：

- 可以写「这也是很多人可能遇到的处境」「我怀疑这不只发生在 AI 领域」，前提是明确这是作者观察或邀请读者共鸣。
- 不可以写「大多数人」「普遍如此」「很多人都」来冒充调研结论，除非实验材料有对应数据或外部可引用来源。
- 吸引力来自具体处境、反差、代价和未解决的问题，不来自夸张标题、恐惧营销或虚构冲突。

## 关键词：让读者找到文章，不让词替文章说话

最终成文要有一组可检索、也能帮助读者理解定位的关键词。它们可以连接当下的讨论，例如 `AI agent`、`agent harness`、`human-in-the-loop`、`vibe coding`、`AI 原生工作流`，但只在与实验事实准确对应时使用。

- 每次生成内容简报时，列出 3-6 个关键词，并分别标注：**事实对象**、**读者正在讨论的叫法**、或**作者的类比**。
- 关键词必须在正文第一次出现时用一句人话解释。比如本实验可称为「内容实验 harness」：它不是另一个模型或平台，而是一套把实验目录、事实、人工确认、审核与平台稿串起来的约束和反馈环境。
- 标题优先用读者能直接感到的冲突；关键词放在副标题、摘要、开头或小标题。除非术语本身就是读者要找的问题，不用热词替代具体处境。
- 不为 SEO 或蹭热度加入实验没有测过的产品、趋势或结论；也不承诺「覆盖热门话题」而不验证当下语境。

## 流程

### 第一步：读取

读实验目录下的：

- `README.md`（必需）——按标题提取 Question / Setup / Log / Data / What Worked / What Failed / Conclusion
- `plan.md`（若存在）——开跑前的剧本。重点看「预期反直觉点」，和 README 实际结果对照：**猜错的地方就是选题最好的开篇**
- `notes/`——所有文件，作为过程细节的补充
- `data/`——量化结果
- `recordings/`——只列文件名和时长，用于视频脚本的片段标注
- `notes/session-timeline.md`（若存在）——从 agent 会话记录提取的真人输入时间线，带时间戳。**对话式工作没有录屏时，这是主要的过程证据**：决策、犹豫、中断、返工都在里面，引用时给出时间戳
- `content-outline.md`（必需，新实验）——实验前由作者确认的背景、读者、已知困难与叙事骨架
- `## Artifacts`（若存在，README 的可选第八段）——这次实验产出的可复用成果指针表。**各平台输出都要带上它**：读者最想知道「这实验产出了什么我能用的东西」

若 `README.md` 缺失或标题不完整，先告诉用户缺什么，不要猜。

新实验若缺 `content-outline.md`，或其中没有「已确认：是」，停在这里要求作者补齐；不要先生成平台稿。回溯补记可以继续，但必须在报告中标记为「未经过实验前内容骨架确认」。

**若 `Log` / `Data` / `What Worked` / `What Failed` 为空**，停下来报告，不要代填。这四段需要「跑实验时发生了什么」的一手信息，而本 skill 只能读实验目录，拿不到那些上下文。该由跑实验的会话在收尾时起草并交人核对。

### 人工事实补充（按需询问）

在蒸馏前检查叙事是否缺少决定性的人类信息。只有缺失会让文章无法诚实成立时，才问 1-3 个具体问题；不要用泛泛的「还有什么补充吗」。优先问：

- **动机与代价**：为什么拖延、卡住或改方向？实际花了多久？哪些部分是人工投入？
- **作者判断**：这次真正改变了什么看法？哪些结论只适用于本次？
- **发布现实**：账号注册、认证、素材补拍、预览、排版、发布与维护中，哪些尚未完成？

把回答写入实验 README 的 `Log` 或 `Data`，标注为「作者补充」及日期；未写入前不得把它当作可复用事实。若用户暂不回答，保留缺口，不用推断填满。

### 第二步：蒸馏中立事实

在生成任何平台内容之前，先产出一份结构化摘要（内部使用，不写文件）。这一步不考虑平台风格：

```
一句话结论:
核心问题:
测了什么:
关键数据: (3-5 条，必须来自 data/ 或 README 的 Data 段，不得杜撰数字)
有效的:
失败的:  (标注每一条的原因)
预期落差: (plan.md 的预期反直觉点 vs 实际结果。无 plan.md 则跳过)
叙事弧线: (为什么选这个实验 → 中间哪些失败 → 成果是什么 → 能否复制。缺一项就是流水账)
最反直觉的发现:
可复用成果: (README 的 Artifacts 段。无则跳过)
可用过程证据: (录屏文件名、会话记录时间戳、git 提交 → 对应内容。分别标注一手/复现/示意)
```

「最反直觉的发现」是选题价值的核心。如果找不到，说明这次实验的内容价值有限，直接告诉用户。

「叙事弧线」决定读者能不能读下去。**客观记录失败和讲好一个故事不冲突**——故事性不是加修辞，是把这四件事讲全：

1. **为什么选这个实验**——当时处在什么状况，为什么是这件事而不是别的。这一拍缺了就是自说自话，读者没有理由点开
2. **中间哪些失败**——真做了才暴露的东西，照实写。这一拍缺了就是产品说明书
3. **成果是什么**——最后拿到了什么，具体到文件和数字
4. **成功能否复制**——换个人、换台机器、换个题目还成立吗？哪些是通用的，哪些是这次特有的

第 4 项最容易漏，也最值钱：只有它能把一次性的经历变成别人能用的东西。写不出来就直说这次不可复制，别硬凑。

「为什么选这个实验」通常藏在动机里，不在 Log 第一句。找不到就问用户：这件事你是在什么处境下开始做的？

各平台顺序不同——小红书把失败提到第一屏，公众号按 1-2-3-4 走，视频用第 1 项做 hook——但四项都得在。

## 中文行文

AI 写中文有固定的病：翻译腔和欧化长句。

- **句子短。** 一句话说一件事。超过三十字就找地方断开
- **主语在前。** 少用「被」；「配置被写在了文件里」写成「配置写在文件里」
- **删掉虚词壳子。** 「进行了修改」→「改了」；「实现了自动化」→「自动化了」；「对于 X 来说」→「X」
- **的地得分清。** 错了会被一眼看出来，直接影响可信度
- **判断标准：读出声。** 读着别扭就重写，不要因为「意思对」就留着

英文平台（site / github）不适用本节，按英文自己的简洁标准写。

### 第三步：生成并确认内容简报

把实验前 `content-outline.md` 与实验后事实合成 `content-brief.md`。这不是平台稿，控制在 400-800 字，只回答：

1. 已知背景和面向读者的问题；
2. 本次发生了什么（只列关键事实）；
3. 核心观点或可用金句（明确标注为作者判断或待确认）；
4. 重要困难、人工投入与未完成的发布动作；
5. 超出内容骨架预期的发现；
6. 结论能说到哪里、不能说到哪里。

写简报时单列一行「读者痛点 / 叙事线」：用一句作者观察说明这次实验可能与哪些人的什么处境有关，并标注它是作者判断，不是统计结论。没有这个连接时，先问作者这次为什么值得陌生人花时间读；不要直接把技术日志展开成平台稿。

再单列「关键词与用法」：每个词写明类型、出现位置和一句解释。没有与事实对应的关键词时宁可少写，不要凑满。

文件末尾固定保留：

```markdown
## 作者确认

<!-- 确认后填写：已确认：是；日期：YYYY-MM-DD；可公开：是/否。 -->
```

生成 `content-brief.md` 后**立即停止**，请作者核事实、补观点并明确确认。只有确认行同时含「已确认：是」与「可公开：是」时，才能在下一次调用进入平台渲染。不要把「用户看过了」或「没有反对」当确认。

### 第四步：选择平台

读取 `platforms/` 下的平台配置。每个平台配置定义：

- 平台别名和触发词
- 输出文件和对应模板
- 写作风格、侧重点、排版要求
- 平台验收清单
- 是否需要下游发布 skill

默认生成所有已配置平台。若用户指定平台，只生成匹配平台。若用户指定的平台没有配置，先告诉用户缺哪个 `platforms/<id>.md`，不要临时硬编一套规则。

新增平台时，只加：

1. `platforms/<id>.md`
2. `templates/<id>/...`

除非平台选择逻辑变化，不要改本 skill 主流程。

### 第五步：平台渲染

用蒸馏结果填充被选平台声明的模板，写入实验目录的 `drafts/<platform>/`：

| 平台 | 配置 | 典型输出 |
| --- | --- | --- |
| 网站 / 静态站 | `platforms/site.md` | `drafts/site/blog.md` |
| GitHub | `platforms/github.md` | `drafts/github/readme-section.md` |
| 小红书 | `platforms/xiaohongshu.md` | `drafts/xiaohongshu/note.md`, `carousel-brief.md` |
| YouTube | `platforms/youtube.md` | `drafts/youtube/scenes.md`, `packaging.md` |

平台适配不是简单改长度。必须按配置改变开头、结构、证据密度、排版、素材需求和 CTA。

### 第六步：出配图

配图不是可选项。文案里引用了图，就必须真的有图。

**写 HTML 源**，不是描述图长什么样。产出到 `drafts/<platform>/assets/<序号>-<用途>.html`，每个文件带尺寸声明：

```html
<meta name="render-size" content="1080x1440">
```

**渲染成 PNG**：

```sh
scripts/render.sh drafts/<platform>/assets
```

路径相对本 skill 的 base directory。脚本用系统 Chrome headless 渲染——本机没有别的渲染器（rsvg-convert / ImageMagick / wkhtmltoimage 全都没装），不要改用它们。

三条规矩：

- **HTML 是源，PNG 是产物。** 改图改 HTML 重渲染，绝不用图形工具改 PNG——那样源和产物就脱钩了。
- **图里的内容同样要脱敏。** 一张讲信息泄露的配图自己带着真名或本机绝对路径，是这套东西能犯的最蠢的错。用户名、邮箱、绝对路径一律换占位符。
- **真实截图不生成。** 需要真实终端截图的列进缺口清单，不用示意图冒充。

来源优先级：真实截图 > 数据卡 > 结构图 > 示意图。重演补拍必须与 git 历史一致，不许为效果伪造报错或时间线。

各平台的尺寸、配色、张数以 `platforms/<id>.md` 的视觉资产段为准。

### 第七步：校验（报告前必须跑）

```sh
../experiment-plan/scripts/validate.sh <实验目录>
```

路径相对本 skill 的 base directory——两个 skill 装在同一个 `skills/` 目录下。**退出码非零必须修完再报告，不许带着 FAIL 交付。**

这一步专门抓模板产出的死链：`site` 和 `github` 模板会链到 `notes/` `data/` `recordings/` `code/`，而约定里这四个目录是按需创建的。目标不存在就删掉那条链接，只列真实存在的，不要留死链。

数字溯源那一项是启发式，录屏序号和时间码会误报，逐条判断，不要为了消警告去改真实数字。

### 第八步：三轮内容审核与修改

每个平台初稿必须经历至多 3 轮「独立审核 → 修改」循环。每轮审核都交给**未参与该稿写作的 sub-agent**；审核者只读事实源、平台配置和当前稿，不接受「读起来不错」作为通过理由。修改由另一名写作 sub-agent 或主 agent 完成，随后进入下一轮审核。

**审核不是聊天消息，必须落文件。** 在实验目录中创建 `internal/`（不面向发布），每轮写一份不可覆盖的 `internal/review<轮次>.md`，例如 `internal/review1.md`。下一轮审核必须先读前一轮报告；修改者也必须逐条对照报告改稿。不要把审核结果只留在会话记录里。

每份报告顶部固定写：

```markdown
# 内容审核 · 第 <轮次> 轮

- 审核者：<sub-agent 名称或会话标识>
- 审核日期：YYYY-MM-DD
- 审核范围：<列出 drafts/ 下的文件>
- 依据：README.md、content-outline.md、content-brief.md、对应平台配置
- 本轮未修改文件：是
```

报告随后按平台分别列出评分表、问题证据和修改任务；文件最后必须有 `## 审核结论`，逐个平台写 `publish-ready` 或 `not publish-ready`。修改者完成后，在下一轮报告的开头列出「上轮任务完成情况」：已完成、未完成、拒绝修改及理由。这样才能看出每一处修改是在回应哪一条审核意见。

每轮输出一张审核表。每项 0-2 分，并给出对应的源文件路径、段落或原文；没有证据不得给 2 分。

| 指标 | 0 分 | 1 分 | 2 分 |
| --- | --- | --- | --- |
| 事实准确与可追溯 | 有编造、矛盾或无来源数字 | 有待核实说法或来源不清 | 事实、数字、状态均可定位到实验材料或作者补充 |
| 结论支撑与边界 | 结论超出证据，或把判断写成事实 | 有边界提示但仍有跳跃 | 证据、作者判断、未知项明确分开，样本/限制写清 |
| 逻辑与叙事 | 背景、过程、发现和结果脱节 | 顺序大致成立但有跳跃或重复 | 动机 → 过程/失败 → 证据 → 成果/限制完整推进 |
| 表达可读性 | 病句、翻译腔、套话或无法朗读 | 偶有冗长、抽象或重复 | 句子顺、具体、有节奏，删去不承载新信息的句子 |
| 平台适配与视觉证据 | 套同一篇文案，图与结论无关 | 有平台格式但第一屏/素材不足 | 开头、结构、CTA、图表都服务该平台读者；关键主张有直观证据 |
| 读者痛点与吸引力 | 只有流水账，读者无法判断与自己何干 | 提到共鸣点但抽象、夸张或脱离事实 | 用作者经历中的具体处境连接读者痛点；不把共鸣写成统计事实 |
| 关键词与语境 | 堆热词、术语无解释，或与实验无关 | 有词但位置生硬或含义模糊 | 3-6 个相关词各有事实对应、清楚解释与自然出现位置 |
| 人工成本与发布状态 | 把草稿误写成自动发布或零成本 | 提到人工但没有具体环节 | 清楚列出注册、审核、补拍、排版、发布等人工动作和就绪状态 |

通过条件：每项至少 1 分、`事实准确与可追溯` 与 `结论支撑与边界` 必须为 2 分、总分至少 14/16。任一硬项为 0 分，立即退回修改。第 3 轮后仍未通过，不得再润色掩盖问题：输出 `not publish-ready`、未通过项、需要人工补充的最小问题集。

审核重点是找问题，不负责改写；写作 sub-agent 只按审核表和事实源改，不得为了提高分数新造素材。作者必须在发布前确认结论、个人经历、平台人工动作和封面/图文顺序。

### 第九步：报告

生成后简要说明：

- 写了哪些文件
- 哪些部分是占位、需要用户补（尤其是结论）
- 数据是否充分，不足则指出缺什么
- 各平台还缺什么素材或人工动作
- 哪些平台适合交给下游发布 skill
- 每个平台最终审核轮次、总分、未通过项与 `publish-ready` 状态

## 各渠道的取舍

各平台来自同一份事实摘要，但取的部分不同。不要把 Blog 缩短当成社交文案，也不要把 Blog 念一遍当成视频脚本。具体规则以 `platforms/` 配置为准。

- **网站 / 静态站**——可信、可引用、可检索。保留方法、数据、复现信息、原始记录链接。
- **GitHub README**——最短。做了什么、结论是什么、怎么复现。
- **小红书**——封面和前三行决定点击。结论前置，短句，可扫读，配图脚本必须具体。
- **YouTube / 视频**——包装和留存优先。保留过程、现场、失败和卡住的瞬间；必须给标题、thumbnail、hook、章节、description、字幕和可切 Shorts。

## 反 AI 腔（全平台通用，不在各平台配置里重复）

AI 写出来的东西有一套固定气味。这些模式在任何平台都不许出现：

| 不要 | 症状 |
| --- | --- |
| 套路化小标题 | 「一、什么是 X」「写在最后」「总结」「结语」 |
| benefit 列表 | 「三大优势」「五个好处」「核心价值」 |
| 空泛 buzzword | 赋能、闭环、生态位、颠覆、范式、护城河 |
| 作文骨架 | 「首先…其次…最后」「不仅…而且…」 |
| 无数据的程度词 | 大幅、显著、极大提升、质的飞跃 |
| 万能收尾 | 「希望对你有帮助」「你学会了吗」「欢迎交流」 |
| 对称排比句 | 「不是 A，而是 B」连用三次以上 |

判断标准很简单：**这句话换个主题还成立吗？** 成立就是废话，删掉。

写实验记录只有一种方式——把具体发生的事按发生的样子写出来。数字、文件名、报错原文、当时的判断。具体本身就是可信度。

## 硬约束

- 数字只能来自 `data/` 或 README 的 Data 段。没有数据就写「待补」，绝不估算。
- 不要写成教程口吻（「首先我们打开…」）。这是实验记录，不是使用说明。
- 标题不用「XX 使用教程」这类形式。用结构性问题或反直觉结论。
- 保留失败。失败是这类内容的主要价值来源，不要为了好看删掉。
- 平台配置的验收清单必须逐项检查；不满足就报告缺口，不要假装完成。
- 小红书、YouTube 等平台发布动作不在本 skill 内执行；只生成可交给发布 skill 的内容包。
