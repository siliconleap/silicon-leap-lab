# AI 能不能把一个故事讲成一支能发的动画视频？

## Question

给一段文字讲的故事——没有分镜、没有素材、没有录像——AI 能不能自己把它变成一支画面连贯、能发出去的动画视频？

## Setup

**环境**

- macOS，Claude Code CLI，模型 Opus 5，Node v24.6.0
- 图像：腾讯云
- 配音：腾讯云 TTS，音色 501000，`Speed=0`
- 渲染：浏览器（片 A 逐帧渲染，片 B 走 Remotion），ffmpeg 合成
- 无 OpenAI API key，无图形编辑软件，无实拍设备

**被测对象**

首选候选是 `illustrated-videos` 这套插画视频流水线。它当时的路线是分层装配：每个 scene 拆成不含主体的背景板，加若干独立生成的带 alpha 的主体、道具与前景层，再合成、加语义动效与字幕。**这条路线在这次被推翻了，换法见 What Worked。**

但它不是前提。步骤 1 先横向调研开源的 story → video 路线，按技术形态分类——素材拼接型（脚本 + 库存素材 + TTS，适合口播和资讯流）、文生视频扩散模型（适合电影质感的短片）、代码合成型（Remotion 这类，适合可控的插画讲解）——判断哪一类匹配本次要的「插画动画」，再从中挑一条装起来实测，A、B 两支片子共用它。没被选中的路线不代表不好，很可能只是适合别的场景，调研结论里要写清楚。调研是分析层面的，不逐个安装。

**任务**

两支片子，同一条流水线，故事类型故意拉开距离。

| 片 | 故事来源 | 为什么选它 |
| --- | --- | --- |
| A | 实验 `2026-08-markdown-only-content-pipeline` 的全过程记录 | 有真实截图和结构图可用，硬信息密集，且能补上那次缺的第四个渠道 |
| B | 一则公有领域童话 | 纯文字输入，零素材，无技术门槛，画面全靠生成 |

A 的素材来源是那个实验目录的全部记录：`README.md` 七段、`notes/session-timeline.md` 的 105 条真人输入、`drafts/youtube/scenes.md` 的 13 个 scene、`internal/review1-6.md`。目录里已有的真实截图与结构图可以进片；没有截图可用的段落，必须由生成的分层插画承担，不许用文字卡片充数。

B 不提供任何图，全部画面生成。

两支都跑完才算完，因为这次要验的不是「能不能讲好那个实验」，是**这套生成能力对故事本身有多挑食**。A 成 B 不成，说明它依赖现成素材；A 不成 B 成，说明它讲不了信息密集的内容；都成，才谈得上通用。

**形式约束**

- 画幅 16:9，1920×1080，两支一致（理由见 `plan.md` 的画幅一节）
- 非口播：不出镜，不用真人画面，旁白只走 TTS
- 全程由 AI 执行，人只做审核和局部微调，每次干预逐条记进 `data/interventions.md`

**判据**

1. 两支片子都在 180 秒以内，且都通过所选流水线自带的 QA
2. 两支里都没有单张静止画面连续超过 8 秒——这是上一支片子被判不合格的直接病根
3. 同一条流水线跑两种故事，人工干预次数各是多少、差在哪。差得越小，通用性越强

**已知短板**

作者无美术、动画、策划、编辑背景，对「精美」的判断只能是主观打分，不构成客观判据。平台账号尚未注册，本次拿不到发布后的真实数据。

## Log

起点是上一个实验留下的一个洞。四个渠道做完三个，视频那一栏写着「失败」——不是没试，是试出一支 4 分 24 秒的成片之后判定不能发。理由很具体：画面是一堆截图的简单拼接，算不上动画，非常不连贯。那次的 README 因此写死了一句「视频不是纯文本，也没法由纯文本生成」。

这次回来推翻它，而且推得更远一点：不只补那个渠道，而是验证「给一段文字讲的故事，AI 能不能自己把它变成动画」。两支片子，故事类型故意拉开——一支讲上一个实验的过程，一支讲一则原创童话。

**第一步是横向调研，不预设用哪条路线。** 十个项目，star 数和最后推送日期全部从 GitHub API 实时拉取。最有用的一列是最后推送日期：ShortGPT 停在 2025-02，StoryDiffusion 停在 2024-09。四类路线里选了代码合成型，理由是判据 2 直接指着它——「没有静止画面超过 8 秒」本质上是要求画面里有编排好的变化，而只有代码能把变化写死并复现。

**第二步是把好的做法整合进选定的那条流水线，结果规模比预想小。** 上一个实验留下的时间轴教训——旁白按句合成、每句时长取自合成端、裁掉头尾静音再按标点补回停顿——读源码发现已经整个在 `illustrated-videos` 里了。真正的缺口在别处：`preflight.mjs` 的三个 provider 白名单里没有腾讯云的生图和 TTS，而实现代码在、文档也写了整整一节。**这台机器上唯一有密钥、唯一跑得起来的组合，校验器会直接拒绝。**

这是上一个实验那个招牌发现的第二次出现，形状一样：脚本支持、文档写了、校验不认，三个文件分开看每一个都对。同一个 bug 后来又出现了第三次——`validate-manifest.mjs` 有自己独立的一份白名单，项目通过了 preflight、跑完全部素材生成和抠图，走到清单校验才被拒。**失败点越靠后，浪费越多。**

**水印那件事绕了四轮。** 仓库里 `providers.md` 写着「`LogoAdd: 0` 去不掉『AI 生成』标，已目视核实」，代码注释写着相反的。作者说网上查到能关，要求核实。我查了腾讯官方文档，三个接口口径一致支持「能关」，于是判定那份一手记录错了并改写了它。实测：传 0 和传 1 生成的两张图右下角一模一样，**一手记录是对的，文档是错的，我改错了**。改回之后，作者去后台打开了一个配置开关，重测——`LogoAdd` 完全按文档行为。完整机制是：参数是真的，但被一个账号级的后台设置 gate 住，而响应里没有任何字段能区分这两种状态。**三方各错一半：文档漏了 gate，一手记录把自己账号的状态当成了系统属性，我漏了实测。**

**角色一致性是第二次判断反了。** 我写下「prompt anchor 加人工检查，本质上是用文字反复约束，靠不住」，并据此建议引入外部厂商。作者说：我记得那套流水线里有处理的。回去读原文，是一套四层机制——结构化锚点格式、稳定部分逐字重复、姿态成组审而非逐张过、漂移只能重生成不许用快转场遮掩。实测六张图，两组都保持住了同一只狐狸。**「靠不住」是没测就下的判断。**

**但真正的短板在姿态。** 按锚点写了 8 个姿态，身份八张如出一辙，姿态基本没有被执行——要「回头看」给正常侧走，要「前蹄抬起悬空」给四蹄着地。挑最差的四个重生成，姿态提到最前、加负向提示词，四个里只好了一个，**而且身份漂了**：强调姿态就必须改写那些本该逐字重复的部分，两个目标在同一段文本里互相挤。

这一下把整条路线的打法改了：**不再指望用不同的图表达不同的动作，动作全部交给 `motion.keyframes`。** 后来那朵「一整片巨大的雪花」也是同样的解法——图错了没重新生成，在分镜里当成单片雪花用了 17 次。**生成端给不了的，编排端往往可以给。**

**两支片子的结果和开跑前的预测相反。** 预期是童话更适合插画、软件实验会更别扭。实际是片 A 更顺：重渲 2 次对 4 次，最长静止画面 2.00 秒对 4.00 秒。原因有两条——A 有四张一手产物承担了最难画的四拍，B 什么都得生成；以及 A 根本不需要角色，抽象概念用道具就能演，**而道具没有身份不会漂移，也不需要姿态**。

**审片拿到的四条意见里，两条是我本该照做的规则。** 翻身那一拍我用侧视图硬转 180 度，尾巴自然朝上翘着——而 `layer-contract.md` 明写姿态变化要用两张图交叉淡入。我读过也引用过这条，但在测出「姿态生成不出来」之后，就默认所有姿态问题只能靠代码变换解决，再没回头试。重试三种说法，成功那条的关键差别是**把相机位置说死了**（「从正上方俯视」），另两条描述身体状态的都失败。**指定视角比描述姿态有效**——这条本该在测姿态那轮就试出来。

## What Worked

### 做法本身换了一条，这是这次最主要的结论

开工时用的是上一套流水线的路线：**先定前景和背景，把主体抠成独立图层，再拼装成画面。**
这条路走了三个版本，三次都被打回。它的问题不在执行：

- 抠图这一步经常不成立。半透明的主体分割不出来，浅色主体在浅色背景上会被当成背景吃掉。
- 就算抠出来了，拼出来的画面也不像一个空间。背景是一次渲染，主体是另一次渲染，
  光照和材质对不上，叠在一起永远像贴纸。
- 更根本的是，这条路默认「画面的变化来自不同的图」，于是每一拍都要新素材，成本和
  返工量都挂在图片张数上。

第四版换成了另一条：

```
先定风格          风格是一份数据，只管材质、光照、配色、动效性格
  ↓
按场景生成整张画面   一次生成一个完整的空间，光照和倒影天生一致
  ↓
用代码让它动       位移、缩放、生长、翻转、滚动，都是算出来的
  ↓
需要时才拆图层     只有确实要独立运动的东西才单独生成，而且必须生成成不透明的
```

**顺序反过来之后，前面那些问题大部分消失了。** 片 A 十四拍里十二拍共用同一张底板，
画面变化全部由代码算——阵列平铺、光丝生长、卡片运动、评分表、终端窗口、表格滚动。
结果是**整支片子只用了 5 张生成图**，上一版是二十多张。

**「需要时才拆图层」这一步现在有明确的判据**：要当图层用的东西，生成时就必须写明它是
不透明的实体，而且不要给参考图（给了会把相邻的东西一起画进来）。从已经生成好的场景里
抠，是最后的选择，不是第一选择。

### 风格是数据，题材是参数

风格预设是一份 JSON，管材质、光照、配色，以及主时长、入场曲线、过冲量这些动效性格。
题材是另一份字符串，只说画面里有什么。两者在编译提示词那一步才合起来。

**所以换风格是换一个词，题材一个字都不用动。** 代价是重新生成图像的接口费用，不是重写
流水线。这条能成立的前提是题材里一个风格词都不能有——写「暖黄色纸雕质感的灯塔」，
换到别的风格下就会打架；只写「灯塔，塔身有三道环形窗，塔顶的灯亮着」。

预设里也不能混进主体规格。有一版的预设开头写着「主体是深灰蓝色磨砂材质的实体物件」，
前半句是材质该复用，后半句「主体是一个物件」不该复用——结果不管题材写什么，模型都先
造一个磨砂盒子出来，题材对画面没有否决权。

### 一段旁白对应一个画面，说不出画面就是没写完

前三版片 A 的返工都出在这里，不在文笔。讲「均值」时画面是一个转动的齿轮，讲「四个平台」
时画面是四张一样的纸——每一句都对，每一拍都没在演那句话。

第四版先写分镜表，每段旁白旁边写清这一拍画什么，写不出来就说明这句话还没想清楚。
这一层现在是强制的产出物。

### 一种运动全片只当一次主角

十四拍用了十四种不同的运动：拉远、横移、光丝生长、沿轨滑入、收拢重合、对峙压近、
条形推进、插入咬合、逐项落评、左右对照、逐行吐出、卡片翻面、表格滚到底、由红转亮。

这条规则的价值不在禁止重复，**而在于逼着为每一拍重新想一遍「这句话到底长什么样」**。
被逼出来的翻面、滚到底、由红转亮，都比默认的「元素飞进来」更贴内容。

### 时长由配音反推，只有一个来源

先定旁白、合成语音、量出每段实际时长，再由它算出每一拍多少帧。改一句旁白，跑两条命令，
十四拍的时长自己更新。这条在这次改了六轮旁白，每一轮都省下手工核对十四处的功夫。

反过来的做法（先定镜头时长再往里塞旁白）会逼着压缩或注水，两种都伤内容。

### 真实产物可以不重绘地进画面

片 A 里三处一手证据——两个自相矛盾的配置文件、独立审核的评分表、校验脚本抓出四处死链
的输出——内容一个像素未改，做成带透视的悬浮面板放进场景，文字在 1920 宽的画面里可读。

**十四拍全是漂亮的 3D 图标会像广告，有三处真东西才像实验记录。**

## What Failed

### 最初的路线本身错了，而且错了三个版本才发现

见上一节。这里只补一句：**每次返工我都在优化执行——换更好的抠图、调更准的坐标、
写更细的提示词——没有一次去问「这条路本身对不对」。** 三个版本、一周时间、一百多张废图，
换来的其实是一次路线判断。

### 判据定错了

两条硬判据（180 秒以内、没有 8 秒以上静止）都通过了，但它们衡量不了片子好不好。
180 秒是内部的软性建议，不是质量线；不出现 8 秒静止只说明画面在动，不说明画面在讲事情。

**片 A 在第一版就能通过这两条**，而第一版是被打回重做的。真正该衡量的是自动化程度和
成片质量，这两件这次都没立成判据。

第三条判据（人工干预次数）问的问题也不对：它数「人被打断了几次」，一次「推翻全部画面
风格重做」和一次「改个错别字」都记 1 条。要衡量通用性，需要的是每次干预的耗时。

### 三次在没有实测的情况下下判断，三次都反了

一次是信官方文档不信仓库里的一手记录；一次是没读原文就断言角色一致性方案靠不住；
一次是把一次抠图失败推广成「这个动画做不成」。**三次的共同点是拿一个结论替代下一次的
观察，三次都是作者一句话掰回来的。**

第三次尤其典型：作者反问「四份没法切图出来吗，直接生成 icon 做不成吗」，才逼出正确的
诊断——不是抠不出来，是抠不了半透明的东西；而独立生成一个不透明的，一次就成了。

### 同一条规则被复制成多份

provider 白名单在两个脚本里各有一份；镜头时长一度在逐帧脚本和 Remotion 入口里各写一遍，
改了一处忘了另一处，同一帧号的画面就对不上——而这种不一致不会报错，只会让音画错位。

**判断该改哪一份的依据是规则想防什么，不是报错长什么样。**

### 手搓了一个更笨的渲染器，而现成的就在同一个仓库里

第四版的动画是逐帧 HTML 加浏览器截图渲的，从头到尾没用 Remotion——而 Remotion 当时正在
被片 B 使用。这不是选型选出来的：探针脚本跑通之后就顺着用下去了，中间没有停下来评估。

后来实测同一个镜头：Remotion 10.4 秒，逐帧 HTML 121.6 秒，画面无差别。**慢十一倍，
外加几千个中间文件。**

### 临时性的坑

这些只在特定组合下出现，记录备查，不构成通用结论：姿态指令在这个模型上首轮 0/8 命中；
浅色主体在浅色背景上抠不出来；供应商水印取决于账号后台一个开关，关着时参数不报错但图
上有水印；渲染器每帧启一个浏览器进程时 CPU 只跑到 5%。完整清单见 `notes/difficulties.md`，
共通 23 条、临时 4 条。

**先说这次的判据立错了。**

两条硬判据——180 秒以内、没有 8 秒以上的静止画面——**都通过了，但它们衡量不了这支片子
好不好**。180 秒是一个内部的软性建议，不是质量线；不出现 8 秒静止只说明画面在动，不说明
画面在讲事情。片子实际该拿来衡量的是两件事：**自动化程度**（多少步不需要人插手）和
**成片质量**（人看完觉得值不值得发）。这两件这次都没有立成判据。

代价是具体的：**B 半天生成完，主观 3 分；A 打磨了接近一周，反复改画面风格、改动画内容、
重做旁白，主观 4 分。** 这一周买到的一分，两条硬判据全都看不见——A 在第一版就能通过它们。

**判据 3 也问错了问题。** 它数「人插手了几次」：A 11 次、B 8 次，差 3 次。但一次「推翻全部
画面风格重做」和一次「改个错别字」在这张表里都记 1 条。真要衡量通用性，需要的是每次干预
的耗时，而这次没记。**这是判据设计的缺陷，不是数据没跑够。**

从这些数字里能读出来的，只剩一条：**共用干预 18 次，比两片各自的都多——这套能力真正的
成本不在「换一个故事」，而在「把能力本身建起来」。**

**那么这次到底做成了什么。**

上一个实验的成果表最后一行写着「视频渠道交付 · 失败 · 试出一版 4 分 24 秒的成片，达不到
可发布标准」。这一次两支片子都出来了：A 一支讲实验过程的动画，B 一支童话。**变的不是模型，
是做法**——分层素材、一段旁白对应一个画面、一种运动全片只当一次主角、时长由配音反推。
同一批接口，上一次做不出来，这一次做出来了。

自动化程度可以照实描述，虽然没有量化：**从旁白定稿到出片这一段基本不需要人**——配音、
每拍时长、渲染、合成是一条命令串起来的，改一句旁白，十四拍的时长会自己跟着变。
**需要人的是前面那一段**：这一拍该讲什么、画面该长什么样、生成出来的图能不能用。
片 A 那一周几乎全花在这里。

**最诚实的一句话是：这套流水线能把「已经想清楚的东西」变成视频，但想清楚这件事它还做不了。**
B 半天出片而只有 3 分，正是因为没人在它身上花时间想。

**成本：29.27 元。** 两支片子加起来的全部接口开销——图像 27.5 元、语音合成 1.77 元，
来自平台实际账单。图像那部分生成了 137 张，成片只用上 18 张（片 A 5 张、片 B 13 张），
**利用率 13%**。

账单没有按片分账，但可以估：片 B 生成 22 张（记录在案），片 A 就是剩下的 115 张；配音按
时长 178 : 75 摊。得到**片 A 约 24.3 元、片 B 约 4.9 元**。

**两片的差距不在成片长度，在试错量。** 片 B 22 张里用上 13 张，片 A 115 张里只用上 5 张。
那 110 张没进成片的图，绝大部分花在找风格上：五轮预设试验、一条走错的写实纸张路线、
卡片墙的三个版本、角色一致性测试。**片 A 的 24 块钱，买的主要不是素材，是排除掉一百多种
不对的做法。** 这也解释了为什么 A 打磨了一周、B 半天就完事。

片 A 只用 5 张还有个原因：这一版十四拍里有十二拍共用同一张底板，画面变化全部由代码算出来
——阵列平铺、光丝生长、卡片运动、评分表、终端窗口、表格滚动都是 DOM 和 CSS，不是图。
上一版是「一拍一张图」，那一版光是素材就有二十多张。**把「变化」从图片挪进代码，成本会
跟着掉一个量级。**
