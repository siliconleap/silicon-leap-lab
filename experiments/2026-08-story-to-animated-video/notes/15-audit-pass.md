# 步骤 12 · 用仓库自带的审计脚本过一遍

**日期：** 2026-08-24
**起因：** 作者说片子仍然不连贯，配置打架那一段没有上下文看不懂，要求整体审视；并问有没有现成的优化 Remotion 工程的方法。

## 有，而且整场没用过

`editorial-video/scripts/audit-project.mjs`。**这是本次最该早点发现的东西。**
我从步骤 3 一路手工看抽帧、调坐标、改关键帧，而仓库里一直有个按 `quality-rubric.md`
七个维度打分、并给出具体到 scene id 的警告清单的脚本。

第一次跑（片 A 改版后）：

```
score 94 / target 88   publishCandidate: true
warnings:
  Hero scenes without a supporting or depth layer: s5, s7, s12
  Hero scenes outside the planning range 3–7: s1..s13（除 s11）
  Long hero scenes with fewer than two independently timed semantic tracks: s5, s7, s12
  Scenes where every layer enters simultaneously: s1,s2,s3,s4,s6,s8,s9,s10,s11,s13
  Primary may be too small for mobile viewing: s1, s2, s8, s11
```

片 B 同时跑：100 分，但同样报「每层同时入场」7 拍、「主体对移动端太小」**全部 8 拍**。

**分数过线不等于片子好。** 94 和 100 都过了 88 的目标线，而作者看到的问题一条都没被
分数拦住——它们全在 warnings 里。

## 作者说的「不连贯」，审计给出了机械层面的解释

最直接的一条是 **`delay` 全为 0**：一拍里所有图层同时入场。观感就是每一拍「啪」一下
整个画面全出来，然后等旁白念完，再「啪」一下换下一拍。**没有建立过程，只有切换。**

判据是这样写的：

```js
const simultaneous = heroScenes.filter((scene) => {
  const layers = layersOf(scene);
  return layers.length > 1 && new Set(layers.map((layer) => layer.delay ?? 0)).size === 1;
});
```

第二条是 **`primary.width / project.width < 0.28`**——1920 宽的画面里主体不足 538px 就算
太小。片 B 八拍全中。

第三条是片 A 的**平均每拍 1.85 层**，而推荐范围是 3–7。画面单薄，也是「不连贯」的一部分：
一拍里只有一个东西在动，切到下一拍又只有一个，中间没有任何延续的元素。

## 改了什么

**一、配置打架那一段补上下文，而且发现问题比想象的严重。**

作者说没有上下文看不懂。回去查才发现更糟：改版后那张矛盾图放在 s3，而 s3 的旁白讲的是
「四个平台的初稿生成出来了，然后我发现没法看」——**图在讲一件事，旁白在讲另一件事。**

现在给它独立一拍，把话说全：

> 翻到根子上，看到一件有意思的事。这条流水线里有两份文件，都是同一次生成出来的。
> 一份写风格要求，明确说：不要陈述完事实就转进列表。另一份是小红书的模板，而它自己
> 就硬编码了三段列表——结果、有效的、踩的坑。一份在定规矩，另一份在违反它。分开读，
> 每一份都挑不出毛病。

**二、每一拍的图层错开入场。** 片 A 按 0 / 14 / 26 帧，片 B 按 0 / 7 / 15 / 23…（雪花实例
本来就该各来各的）。主体先到位，次级元件后跟，景深层最后淡入。

**三、主体一律放大到 ≥ 576px**（阈值 538，留余量）。片 B 改了 10 处。

**四、片 A 给薄的拍补景深层。** 那三拍是证据卡拍，主体是不可改动的一手产物，加太多层
会挡住可读性——所以补的是低透明度的次级元件（笔停在改动行旁边、印章一轮盖一个、
放大镜停在两份文件的缝上），并给这三拍写了 `layerPlanRationale` 说明为什么层数少。

**五、总时长压回 180 秒以内。** 补了矛盾那一拍之后旁白涨到 194.42 秒，超过判据 1。
逐句收紧了七处（删「生成来自统计概率」这类解释性从句、合并重复的「半天/一周多」），
降到 176.91 秒。

## 顺带定了编码档位

作者问视频存哪，牵出一件本该早做的事：**CRF 18 对剪纸这种大色块内容是浪费。**
实测同一支片子 CRF 18 / 23 / 26 分别是 109 / 42 / 26 MB，截深色底小字的证据卡放大对比，
**三档看不出区别**。渲染改用 CRF 23。

这不只是省空间——26 MB 级别的片子才谈得上放在自己站点上直接播，109 MB 的只能依赖平台。
