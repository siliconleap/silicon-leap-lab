**唯一真正值得借鉴的是 IndexTTS2 的时长控制。** 它的 README 原话是「The first autoregressive TTS model with precise synthesis duration control, supporting both controllable and uncontrollable modes」。

为什么这条重要，要从我们现在的时间轴模型说起。现在是**先配音，再按实测时长排画面**——这个顺序对，因为它消掉了对轴。但它有个隐含代价：**画面时长由旁白说了算**。一个 scene 的动作需要 6 秒才演得清楚，而那句旁白只有 3 秒，画面就只能被压缩或者硬撑。

时长可控的 TTS 把这个约束反过来：先定 scene 需要多长，再让语音去适配。对判据 2 是直接相关的——「没有单张静止画面超过 8 秒」的反面是「动作要有足够的时间演完」。

其余的能力（零样本克隆、情感控制、定制音色）对本次不构成瓶颈：两支片子都是非口播的第三人称旁白，一个稳定音色够用。

**但有个硬约束：这些全是本地模型。** 这台 macOS 机器没有 CUDA，推理走 CPU 或 MPS，速度未知。所以这条不直接实装，改成**步骤 2 里限时 30 分钟的探测**：装上跑一段，测实际耗时。跑得动就作为可选 provider 接进来，跑不动就记下来当后续，绝不为它拖住主线。

### 比价格重要得多的：参考图条件化

**当前实现是纯文生图，给不了参考图。** 而 B 那支童话最大的风险就是角色一致性——同一个兔子在八个 scene 里分开生成，必然长得不一样。`editorial-video` 现在的对策是 prompt anchor 加 QA 人工检查，本质上是「用文字描述反复约束」，靠不住。

这两年图像模型多了一类能力正好治这个：给一张参考图，生成同一角色的新姿态、新场景。

| 模型 | 权重 | 能力 |
| --- | --- | --- |
| FLUX.1 Kontext [dev] | 开源权重 | 上下文内编辑，跨轮迭代保持角色和物体 |
| Qwen-Image-Edit | Apache-2.0 | 语义与外观编辑，多视角、多表情下的角色一致性 |

两者硅基流动都有 API，跟上面那张价格表是同一个平台。**所以一次改动同时拿到两样东西：更便宜，且多一项当前实现完全没有的能力。**

这条服务判据 1——B 那支片子如果角色一致性崩了，就不是「不够精美」，是做不出成片。按 `plan.md` 的移植规则（只移植直接服务判据 1、2 的），它够格。

### 本地方案：调研了，不用

ComfyUI（129,023★，2026-08-23 仍在推）、Z-Image（11,923★）、Qwen-Image（8,255★）都能本地跑，零 API 成本。不用的理由和文生视频一样：这台机器没有 GPU，且本次目标是出两支片子，不是搭本地推理环境。记进后续。
